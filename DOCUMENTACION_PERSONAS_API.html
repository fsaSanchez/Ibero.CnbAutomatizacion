Sistema PUI — Alertas de Personas Desaparecidas · Universidad Iberoamericana

📍 Ruta base: /api/personas 📦 5 endpoints documentados 📅 Mayo 2026

Arquitectura del controlador

El controlador PersonasController es la puerta de entrada pública y administrativa para la gestión de personas desaparecidas registradas en el sistema. Coordina dos servicios principales: uno para consultar, eliminar y publicar fichas, y otro específico para la carga manual de PDFs.

HTTP Request→ PersonasController  (valida parámetros, decide qué servicio llama)
Servicios→ PersonaDesaparecidaService  |  CargaPdfManualService
Sub-servicios→ PublicacionFacebookService  |  PdfExtractorService  |  RegexExtractorService  |  OpenAiExtractorService
Repositorios→ Base de datos SQL Server
ℹ️ Todos los endpoints devuelven siempre HTTP 200 con un objeto CommonResponse que incluye los campos success, code, message y data. Los errores no lanzan excepciones HTTP; se expresan mediante success: false dentro de la respuesta.

Índice de endpoints

  1. GET /api/personas — Listar personas con filtros y paginación
  2. GET /api/personas/{id} — Consultar detalle completo de una persona
  3. DELETE /api/personas/{id} — Eliminar (desactivar) una ficha
  4. POST /api/personas/{id}/publicar — Publicar manualmente en Facebook
  5. POST /api/personas/cargar-pdf-manual — Cargar un PDF de ficha oficial manualmente
GET /api/personas Público Listar personas con filtros y paginación

¿Para qué sirve?

Devuelve una lista paginada de personas desaparecidas registradas en el sistema. Es el endpoint principal del portal público: alimenta la pantalla de búsqueda donde cualquier visitante puede buscar por nombre, folio, lugar o fecha. No requiere autenticación.

Parámetros de entrada (URL query string)

ParámetroTipoRequeridoDescripción
folio texto Opcional Folio Único de Identificación (FUI). Búsqueda parcial o exacta.
nombre texto Opcional Nombre de la persona. Permite búsqueda parcial (contiene).
estado texto Opcional Estado de procesamiento del registro: completo o incompleto.
fechaHechos fecha (yyyy-MM-dd) Opcional Filtra por la fecha en que ocurrió la desaparición.
busqueda texto Opcional Búsqueda libre que cruza nombre, lugar de hechos y características físicas.
pagina número entero Opcional (default: 1) Número de página para la paginación.
tamanioPagina número entero Opcional (default: 20) Cantidad de registros por página.

Flujo paso a paso

  1. El controlador recibe la solicitud y pasa directamente todos los filtros y valores de paginación al servicio. No realiza validaciones adicionales en este punto.
  2. El servicio consulta la base de datos a través del repositorio de PersonaDesaparecida. La consulta aplica los filtros indicados directamente en SQL Server para no cargar registros innecesarios en memoria.
  3. La base de datos devuelve dos valores: la lista de personas de la página solicitada y el total de registros que coinciden con los filtros.
  4. El servicio construye la respuesta paginada que incluye: los registros de la página actual, el total de registros encontrados, el número de página actual y el tamaño de página usado. Cada registro incluye los datos de resumen: nombre, FUI, edad, lugar de hechos, fecha, estado de procesamiento y si ya fue publicado en Facebook.
  5. Devuelve la respuesta al cliente con success: true y la lista paginada en el campo data.

Servicios que consume

PersonaDesaparecidaService PersonaDesaparecidaRepository

Tablas de base de datos involucradas

persona_desaparecida (lectura) foto_persona (no en esta consulta)

Qué devuelve

datos — Lista de personas (resumen). Cada una incluye: id, nombre, FUI, edad, sexo, lugar de hechos, fecha de hechos, estado de procesamiento, flag de publicado en Facebook, ruta de foto principal.
totalRegistros — Total de personas que coinciden con los filtros (para calcular páginas).

GET /api/personas/{id} Público Consultar detalle de una persona

¿Para qué sirve?

Devuelve todos los datos completos de una persona desaparecida específica, incluyendo sus fotos. Es el endpoint que alimenta la pantalla de detalle del portal cuando el visitante hace clic en "Ver más" desde la lista. Tampoco requiere autenticación.

Parámetros de entrada

ParámetroTipoRequeridoDescripción
id número entero (long) Requerido Identificador único numérico de la persona en el sistema. Va en la URL.

Flujo paso a paso

  1. El controlador recibe el ID desde la URL y lo entrega directamente al servicio.
  2. El servicio busca en base de datos la persona con ese ID. La consulta incluye también sus fotos asociadas en la misma operación (join).
  3. Si la persona no existe (o está desactivada), el servicio devuelve una respuesta de error con código 404 y el mensaje "Persona desaparecida no encontrada". El HTTP sigue siendo 200.
  4. Si existe, construye la respuesta de detalle completa con todos los campos extraídos del PDF y la lista de fotos asociadas.
  5. Devuelve la respuesta con success: true y los datos completos en el campo data.

Servicios que consume

PersonaDesaparecidaService PersonaDesaparecidaRepository

Tablas de base de datos involucradas

persona_desaparecida (lectura) foto_persona (lectura)

Qué devuelve

data — Objeto completo con todos los campos: nombre, FUI, edad actual, edad al momento, sexo, género, nacionalidad, lugar de nacimiento, lugar de hechos, fecha de hechos, fecha de percatamiento, características físicas, señas particulares, prendas de vestir, autoridades competentes, carpeta de investigación, idioma, discapacidad, estado de procesamiento, campos incompletos, flag de publicado en Facebook, fecha de publicación, y lista de fotos con sus rutas en disco.
DELETE /api/personas/{id} Solo admin Desactivar una ficha del sistema

¿Para qué sirve?

Elimina lógicamente una ficha de persona desaparecida del sistema. La eliminación no borra el registro de la base de datos; simplemente lo marca como inactivo para que deje de aparecer en las consultas del portal. Este diseño preserva la trazabilidad histórica y permite auditorías.

⚠️ Este endpoint requiere autenticación de administrador. Actualmente el sistema tiene la autenticación comentada durante la fase de desarrollo. Antes de salir a producción se debe habilitar el atributo [Authorize] en el controlador.

Parámetros de entrada

ParámetroTipoRequeridoDescripción
id número entero (long) Requerido Identificador único de la persona a desactivar. Va en la URL.

Flujo paso a paso

  1. El controlador recibe el ID y lo pasa al servicio sin procesar nada adicional.
  2. El servicio busca la persona en base de datos por su ID.
  3. Si no existe, devuelve error con código 404. El registro HTTP sigue siendo 200.
  4. Si existe, realiza el soft delete:
    • Pone el campo Activo en false.
    • Actualiza el campo FechaActualizacion con la fecha y hora actual (UTC).
  5. Guarda los cambios en base de datos.
  6. Devuelve confirmación con success: true y el mensaje "Persona eliminada correctamente".
ℹ️ La persona sigue existiendo en la base de datos. Su historial de correos, archivos y bitácora permanece intacto. Solo deja de ser visible en el portal y en futuras publicaciones de Facebook.

Servicios que consume

PersonaDesaparecidaService PersonaDesaparecidaRepository

Tablas de base de datos involucradas

persona_desaparecida (lectura + escritura)

Qué devuelve

success — true si se desactivó correctamente, false si no se encontró.
message — "Persona eliminada correctamente" o mensaje de error.
POST /api/personas/{id}/publicar Solo admin Publicar manualmente en Facebook

¿Para qué sirve?

Permite que un administrador publique manualmente la ficha de una persona desaparecida en la página de Facebook del sistema, sin esperar al job automático nocturno. Se usa cuando se quiere dar difusión urgente o cuando el scheduler no ha podido publicarla.

⚠️ Este endpoint requiere autenticación de administrador. Igual que el DELETE, la autenticación está comentada en la fase de desarrollo.

Parámetros de entrada

ParámetroTipoRequeridoDescripción
id número entero (long) Requerido Identificador único de la persona a publicar. Va en la URL.

No requiere cuerpo (body) en la solicitud. Solo el ID en la URL.

Flujo paso a paso

  1. El controlador recibe el ID y lo entrega al servicio de personas.
  2. El servicio de personas verifica que la persona exista. Si no existe, regresa error 404.
  3. Delega la publicación al servicio de Facebook indicando que el tipo de publicación es "manual" (a diferencia del tipo "automatica" que usa el scheduler).
  4. El servicio de Facebook verifica que la persona no haya sido publicada ya. Si su flag de publicada es true y el tipo es "manual", regresa error inmediatamente para evitar duplicados en la página.
  5. Verifica las credenciales de Facebook en la configuración (PageId y AccessToken). Si faltan, regresa error de configuración.
  6. Lee el texto de información de contacto desde la tabla de configuración del sistema para incluirlo al pie de la publicación.
  7. Construye el texto (caption) de la publicación con este formato:
    • Encabezado: "🔴 ALERTA DE PERSONA DESAPARECIDA"
    • Nombre completo
    • Edad (si está disponible)
    • Lugar de la desaparición (si está disponible)
    • Fecha de la desaparición (si está disponible)
    • Número de carpeta de investigación (si está disponible)
    • Texto de información de contacto
  8. Incrementa el contador de intentos de publicación en el registro de la persona.
  9. Intenta publicar en la API de Meta (Facebook Graph API):
    • Si la persona tiene foto en disco → publica usando el endpoint de fotos de Facebook (/photos), que sube la imagen y el caption juntos.
    • Si la persona no tiene foto → publica usando el endpoint de texto (/feed) con solo el caption.
  10. Registra el intento en la bitácora de publicaciones independientemente de si tuvo éxito o falló. Guarda: la persona, la red social, el tipo (manual), el estado (exitosa/fallida), el ID del post en Facebook si fue exitosa, o el mensaje de error si falló.
  11. Si la publicación fue exitosa:
    • Actualiza el flag FlagPublicadoFacebook a true en la base de datos.
    • Guarda la FechaPublicacionFacebook con la fecha actual.
    • Devuelve confirmación con el ID del post generado en Facebook.
  12. Si falló: actualiza la fecha de modificación y devuelve error con el detalle del problema (error de red, token vencido, etc.).

POST /api/personas/cargar-pdf-manual Solo admin Cargar una ficha oficial en PDF manualmente

¿Para qué sirve?

Permite registrar una nueva persona desaparecida en el sistema subiendo directamente el PDF de la ficha oficial del gobierno, sin necesidad de que llegue por correo electrónico. Activa exactamente el mismo proceso de extracción de datos que el flujo automático (Regex + OpenAI como respaldo), pero se puede iniciar desde el portal administrativo en cualquier momento.

Parámetros de entrada

ParámetroTipoRequeridoDescripción
archivo archivo (multipart/form-data) Requerido El archivo PDF de la ficha oficial. Debe ser tipo PDF y no superar 10 MB.

Validaciones que realiza el controlador

  1. ¿Se recibió un archivo? Si no se envió ningún archivo o está vacío, regresa error inmediatamente con el mensaje "No se recibió ningún archivo."
  2. ¿Es un PDF? Verifica tanto el tipo de contenido (Content-Type) como la extensión del nombre del archivo. Si no es PDF, regresa error "Solo se aceptan archivos PDF."
  3. ¿Pesa menos de 10 MB? Si supera el límite, regresa error "El archivo supera el límite de 10 MB."

Flujo completo paso a paso (si pasa las validaciones)

  1. El controlador convierte el archivo a un arreglo de bytes en memoria. Esto es necesario porque el servicio de negocio no puede acceder directamente a archivos HTTP; el controlador hace esta traducción antes de delegar.
  2. Entrega los bytes y el nombre del archivo al servicio de carga manual, que a partir de aquí ejecuta todo el proceso.
  3. Consulta la configuración del sistema para obtener las rutas donde se guardarán el PDF y las fotos extraídas. Usa las claves ruta_almacenamiento_pdfs y ruta_almacenamiento_fotos de la tabla de configuración. Si no existen, usa valores por defecto.
  4. Guarda el PDF en disco con un nombre único: MANUAL_[fecha y hora]_[nombre original].pdf. Si la carpeta no existe, la crea automáticamente. Si no puede guardar (por permisos o espacio), regresa error en este punto.
  5. Crea un registro de correo sintético en la base de datos para mantener la misma estructura de trazabilidad que el flujo automático.
    • Asigna un identificador único con el prefijo MANUAL- seguido de un código aleatorio.
    • El remitente queda registrado como "carga-manual".
    • El estado inicial del correo queda en "pendiente".
  6. Crea un registro de archivo de correo vinculado al correo sintético, con la ruta del PDF guardado en disco, el tamaño y el tipo de contenido.
  7. Extrae el texto del PDF usando la librería PdfPig, que lee las palabras del documento en el orden en que aparecen.
  8. Aplica extracción por expresiones regulares sobre el texto extraído para identificar los 14 campos estructurados de la ficha: nombre, FUI, edad, sexo, lugar, fechas, características físicas, carpeta de investigación, etc. Si todos los campos se extraen correctamente, el proceso no necesita conectarse a ningún servicio externo.
  9. Si faltan campos después de la extracción por regex, activa el respaldo con inteligencia artificial:
    • Envía el texto completo del PDF al modelo GPT-4o-mini de OpenAI.
    • Le indica exactamente cuáles son los campos faltantes para que intente completarlos.
    • Combina lo que extrajo el regex con lo que completó la IA.
  10. Verifica los campos mínimos obligatorios: si el FUI (Folio Único de Identificación) o el Nombre no pudieron extraerse por ningún medio, el proceso se detiene.
    • Marca el correo sintético con estado "error" en base de datos.
    • Registra el error en la bitácora general.
    • Devuelve error explicando que el PDF no parece ser una ficha oficial válida.
  11. Determina el estado de la extracción:
    • Si todos los campos están completos → estado "completo".
    • Si aún faltan campos aunque se usó IA → estado "incompleto".
  12. Guarda el nuevo registro de persona desaparecida en la base de datos con todos los campos extraídos, el estado de procesamiento y la fecha de creación.
  13. Intenta extraer y guardar la foto de la ficha:
    • Busca imágenes embebidas dentro del PDF.
    • Si encuentra una, la guarda en disco con el FUI como nombre de archivo.
    • Registra la foto en base de datos vinculada a la persona, marcándola como foto principal.
    • Si no hay foto o falla la extracción, continúa sin interrumpir el proceso (solo registra una advertencia interna).
  14. Actualiza el estado del correo sintético con el resultado final (completo o incompleto) y la fecha de procesamiento.
  15. Registra la operación en la bitácora general con el tipo "CARGA_PDF_MANUAL", el estado, el FUI encontrado, y los IDs del correo y la persona creada.
  16. Devuelve la respuesta al portal con los datos de lo que se creó: ID asignado, nombre, FUI, estado de la extracción y lista de campos que quedaron incompletos (si los hay).

Qué devuelve

En caso de éxito (success: true):
idPersonaDesaparecida — ID numérico asignado al nuevo registro en el sistema.
nombre — Nombre extraído del PDF.
folioUnicoIdentificacion — FUI extraído del PDF.
estado — "completo" si se extrajeron todos los campos, "incompleto" si faltaron algunos.
camposIncompletos — Lista de los nombres de los campos que no se pudieron extraer (vacía si estado es "completo").
En caso de error (success: false): mensaje descriptivo del problema (archivo no guardable, PDF no válido, o FUI/Nombre no extraíbles).
🚫 Si el PDF no contiene el Folio Único de Identificación o el Nombre legibles (campos obligatorios en base de datos), el sistema no guarda ningún registro de persona. Solo queda el registro de correo sintético con estado "error" y la entrada en bitácora. El archivo PDF sí permanece en disco.
